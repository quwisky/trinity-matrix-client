`native/crypto` is a Rust crate that runs the same `matrix-sdk-crypto` release as the WASM package behind one JSON call surface, for the phone apps. **Used by the Android app; iOS, web and desktop use WASM.** The crate's [README](https://github.com/quwisky/trinity-matrix-client/blob/main/native/crypto/README.md) is the reference for its call surface, store and key rules, and JNI wrapper.

## Build and test {#build-test}

```bash
cd native/crypto
cargo fmt --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features
cd ../..
pnpm nx run scripts:native-crypto-interop
```

The interop target drives the crate's command-line binary and the repository's WASM package as two devices and compares their answers and request shapes with a golden file. It also runs the contract tests, which run each finished native call and the same WASM call side by side and expect the same answer, including every trust answer about devices and identities, and every step, change event and sent request of each verification flow (SAS, QR codes, cancels) in all four pairings of native and WASM devices, and the secrets inbox and bundle, room key bundles for shared history, dehydrated devices and the remaining machine calls in both mixed pairings. The timeout case waits 61 seconds. Without cargo both are skipped locally and fail in CI. CI runs these checks in the `Native crypto (Rust)` job when the crate, its scripts, the WASM version, the facade, the matrix-js-sdk patch or the workflow change.

## Surface status {#surface}

`native/crypto/surface.json` lists every WASM class and member the installed matrix-js-sdk uses. Each member of a stateful class (one backed by the machine or its store) is `done` (a native call answers it, proven by a contract-test case), `planned`, or `shim` (the JavaScript shim answers it without a native call, such as `free()`). Value types are listed as pure JavaScript; stateless helpers such as `BackupDecryptionKey` stay on WASM. Nothing is `planned`: every stateful member is a native call or a shim.

`pnpm nx test scripts` fails when matrix-js-sdk uses a member the manifest lacks or no longer uses one it lists, when a `done` member has no contract case, when a member is `planned` without being listed in `ALLOWED_PLANNED` (`scripts/native-crypto-surface.mjs`, empty), or when this table disagrees with the manifest. After a matrix-js-sdk bump, run `node scripts/native-crypto-surface.mjs write`: new members arrive as `planned`, so the check fails until each is a native call or a shim, and members of `OlmMachine` need an area as well.

The libolm migration (`Migration.*`) is not ported. matrix-js-sdk migrates only from a legacy crypto store that holds data; Trinity passes none to `createClient`, so js-sdk's default empty `MemoryCryptoStore` is used and the migration never runs. The same spec fails if the app starts passing a legacy store or pickle key, or sets a store factory.

## The JavaScript shim {#shim}

The shim lets matrix-js-sdk's own crypto layer (`initRustCrypto`) run on the crate. It lives in `libs/native/crypto-backend/src/native` and loads only through `installNativeCrypto` from `libs/native/crypto-backend/src/index.ts` (`@trinity/crypto-backend`), a dynamic `import()` that the app makes on Android, before the first account starts crypto (see [Run it on Android](#android)). `installNativeCrypto({ bridge, storeDirectory })` points the static factories of the real WASM classes (`StoreHandle.open` and `openWithKey`, `OlmMachine.initFromStore` and `initialize`, `Migration.*`) at the crate. Every other export stays the WASM package's own object. Install it before anything initialises crypto: a WASM machine made earlier stays on WASM. One process runs one backend: once installed, every account is native. It returns `uninstallForTests`, which puts the originals back for tests; after it, the next `initRustCrypto` runs on WASM beside the crate's machines, two backends in one process, which only the SDK test bed does.

- A factory returns a stand-in for the WASM class: its prototype sits on a guard of the real prototype, so `instanceof` holds and every member the shim does not implement throws "… is not implemented on native crypto" instead of reaching wasm with no pointer. The stand-ins own no wasm memory; their `free()` releases nothing.
- Values the crate returns become real WASM objects where JavaScript can construct the class (identifiers, every outgoing request class, `RoomSettings`), and guarded value objects of the class otherwise (`DecryptedRoomEvent`, `EncryptionInfo`, `MegolmDecryptionError`, …).
- The bridge is `call(request, machine)` and `callBatch(requests, machine)` over the crate's JSON; every request of one call is for `machine`. The calls a machine gets in one JavaScript task go as one batch, split to stay under 1 MB, answered in call order, and one refused item fails only its own call; each machine gets its own batch. Batches go to the bridge one at a time, unless the bridge sets `concurrentMachines` (the Android plugin, one thread per machine), when each machine's batches go in order beside the other machines'. The CLI bridge runs one call at a time. Each batch also polls its machine's events, and those reach matrix-js-sdk's callbacks before any call of the batch settles.
- `StoreHandle.openWithKey` opens `<storeDirectory>/<store name>` with the raw key; `StoreHandle.open` with a store name is refused, and without one it is a memory store. A wrong key fails at `init`. A bridge that sets `ownsStores` (the Android plugin) opens each machine's store itself: `StoreHandle.open(<store name>)` then sends `init` with no path or key, and a memory store (`open(null)`, `OlmMachine.initialize`), a passphrase and `openWithKey` are refused, so JavaScript never holds a store key.
- A machine the crate dropped (a call answered `Panic`, or `UnknownMachine` after one) is reloaded from its store with `init`, and a call that is safe to replay runs once more; `REPLAYABLE` in `src/native/machine.ts` lists them and says why the others (`markRequestAsSent`, `shareRoomKey`, the encrypt calls including `encryptToDeviceEvent`, `invalidateGroupSession`, `bootstrapCrossSigning`, `pushSecretToVerifiedDevices`) are only rejected. The trust setters replayed carry the same key as their first try, so a replay cannot reach a changed device or identity. A replayed sync input is safe: `scripts/native-crypto-replay.test.mjs` shows that a reloaded machine answers an Olm message it already decrypted as undecryptable, keeps the room key and uploads no published one-time key again.
- A machine is lost when the bridge fails, times out (a batch gets the longest limit of the calls it holds: 10 minutes for `init` and room key exports and imports, 5 minutes for the sync inputs, `shareRoomKey`, `markRequestAsSent` and `getMissingSessions`, 60 seconds for the rest; `slowTimeoutMs`, `heavyTimeoutMs` and `timeoutMs` change them, and a batch still waiting after 60 seconds is logged), answers a poll with something other than events or with an event that does not convert, fails three polls in a row, or when the reload fails. Then `onMachineLost(reason, machine)` is called once, every other call rejects with `NativeMachineLostError`, and `receiveSyncChanges` and `receiveSyncChangesMsc4186` never settle. matrix-js-sdk's sync (`processSyncCryptoChanges` in `sync.ts`) logs a rejected sync input and goes on, and its next request with the new `since` token lets the server delete the to-device events (room keys, Olm messages) the machine never saw; a sync input that never settles keeps the sync loop from sending that request, so a client started again on the same store receives them. The host must stop the client on `onMachineLost`. The machine keeps its `init` parameters, store key included, for a reload until it is closed or lost. The queue lets go of the parameters of calls that carry secrets once the batch text is with the bridge (see the error text rule below).
- Error text: nothing the bridge says, and nothing from parsing its answer, enters a shim error's message, `cause` or details, in any batch: a bridge or parser may quote the request or the answer, and either can hold keys or plaintext. Transport failures, timeouts, a refusal of the whole batch, and an answer that is not JSON or not the batch get fixed messages with a `kind` (`NativeBridgeError`: `failed`, `timedOut`, `malformed`) or a `code` (`NativeCryptoError`; a code that is not a plain word becomes `BridgeRefused`). The only text let through is the crate's own `message` of a well-formed per-call error, which the crate keeps free of key material. Calls on `QUIET_METHODS` (their parameters carry key material or plaintext: `init`, `saveBackupDecryptionKey`, `importCrossSigningKeys`, the room key imports, the encrypt calls, and the secrets bundle, dehydration, QR scan and room key bundle sharing and receiving calls) and on `SECRET_ANSWER_METHODS` (their answers do: the cross-signing and room key exports, `getBackupKeys`, `getSecretsFromInbox`, the secrets bundle export, the dehydration key, QR bytes, and a room key bundle's file key as `buildRoomKeyBundle` and `getReceivedRoomKeyBundleData` answer it) get the code only, without message or details; the queue also drops the parameters of `QUIET_METHODS` calls once the batch text is with the bridge, and a replayable one is sent again from the parameters its caller holds until it settles. Sync inputs are on neither list (ciphertext and key counts), nor is `decryptRoomEvent` (a failed decryption returns no plaintext, and matrix-js-sdk needs its error details). A call added later that carries a secret, either way, goes on its list. The `debugBridgeErrors` option puts the bridge's text back for calls on neither list, for local diagnosis; never enable it in a release build. The SDK test bed enables it.
- A failed or malformed poll calls `onEventsDropped`, as a non-zero `dropped` does, and then the shim makes matrix-js-sdk check again: it calls the room key callback with every Megolm session that failed to decrypt since (matrix-js-sdk then retries the events waiting for each, as when a key arrives), and every verification mirror reads its object again in place and runs its callbacks if it changed. One such refresh runs at a time, and a failed poll in its own batches starts no other. Answers that would read as a legitimate "none" or a trust answer (`getMissingSessions`, `getRoomSettings`, `isBackupEnabled`, `getIdentity`, `getDevice`, `getUserDevices`, `crossSigningStatus`, `verifyBackup`, the encryption info of an event) are checked and fail closed with `UnexpectedAnswer` when their shape is wrong.
- Devices, identities and backup keys (`src/native/trust.ts`) are stand-ins built from the crate's snapshot: `Device`, `UserDevices`, `OwnUserIdentity` or `OtherUserIdentity` by the snapshot's `kind`, and `BackupKeys`, whose `decryptionKey` is a real `BackupDecryptionKey` (a new copy on each read, as WASM's getter gives). Every getter matrix-js-sdk reads answers synchronously from the snapshot; every method is a call that carries the key the snapshot was read with (`ed25519Key` for a device, the public `masterKey` for an identity) and is refused in JavaScript, before anything is sent, when the snapshot holds none. A device or identity that changed since fails with `NativeCryptoError` code `StaleObject` (one the machine no longer knows: `UnknownDevice`, `UnknownIdentity`); matrix-js-sdk's call (`setDeviceVerified`, `pinCurrentUserIdentity`, …) rejects with it and nothing is trusted. WASM's object would instead act on whatever device or identity now has that ID. What is live follows matrix-sdk-crypto 0.19.1: an object's own change is. WASM's `Device.setLocalTrust`, `OwnUserIdentity.verify` and `withdrawVerification`, and `OtherUserIdentity.pinCurrentMasterKey` and `withdrawVerification` update the trust state the same object holds, so the stand-in reads its device or identity again before the call's promise resolves; if by then it is gone or has another key, the stand-in is spent and its reads throw `StaleObject` instead of answering. `Device.verify` and `OtherUserIdentity.verify` only sign, so neither object's answers change. A change made elsewhere (a key query after a sync, a reset, local trust set through another object of the same device) reaches neither: WASM builds each object from the store's data when it is read, and its persistent stores give a new copy each time (only its in-memory store shares a device's local trust between objects). matrix-js-sdk reads a device or identity again for each trust question.
- `Device.encryptToDeviceEvent` refused for a device replaced since it was read rejects, and matrix-js-sdk's `encryptToDeviceMessages` (a `Promise.all` over the devices) then fails the whole batch, as it does on WASM when any one device fails (no Olm session, for one). WASM itself would not fail there: it would encrypt for the replaced device's old keys, which the device now under that ID cannot decrypt. The batch failing is what the app sees, and the app can send it again.
- Verification (`src/native/verification.ts`): `VerificationRequest`, `Sas` and `Qr` are live mirrors, one per flow and kind, kept in a registry. The crate's `verificationRequestChanged` and `verificationChanged` events update them while the batch that caused them is delivered, before its calls resolve: every event of the poll is checked first, then every mirror takes its snapshot, then the `registerChangesCallback` callbacks run in the events' order, so a SAS callback already reads its request's end from the same poll, and a callback that throws stops no other. A change of a flow the registry no longer holds is ignored. Every getter matrix-js-sdk reads synchronously answers from the mirror; `timeRemainingMillis` counts down from the snapshot's `expiresAtMs`. `getVerificationRequest(s)` answer from the registry, so the same flow is always the same object; an incoming request is fetched before the sync input or in-room event that brought it resolves; a fetch that fails is tried once more, then again on each sync input, and calls `onEventsDropped` (the crate reports a request's changes only once an answer handed it out). A request event that finds its flow already Transitioned means its SAS or QR code was replaced (by a SAS, or by the start that won the tie), so the flow gets a new stand-in, as WASM's `getVerification()` shows another object, and the replaced one refuses to act (`StaleObject`). `Sas.confirm` sends the decimals that object last handed out through `emoji()` or `decimals()`, or those another object of the flow handed out, never ones a later event brought: a SAS replaced after the user saw it is not confirmed: the shim cancels the flow with `m.mismatched_sas` and answers that cancellation, which matrix-js-sdk sends, so both sides end at once. `UnknownVerification` from cancelling or accepting a flow the mirror saw done or cancelled answers "no request", as WASM; on any other flow it rejects. A flow that is over stays listed until the next sync input, when upstream collects it; `close`, a reload and a lost machine empty the registry. The calls WASM makes synchronously (`acceptWithMethods`, `cancel`, `Sas.accept`, `cancelWithCode`, `Qr.reciprocate`, `confirmScanning`, `toBytes`, `requestVerification`, `verificationRequestContent`) return promises: the matrix-js-sdk patch awaits them, and runs the three cancels inside synchronous methods (`Verifier.cancel`, the SAS callbacks' `mismatch` and `cancel`) as detached blocks that log a failure. It also passes the scanned bytes beside the `QrCodeScan`, which keeps them in wasm memory.
- Secrets, bundles and dehydrated devices: `exportSecretsBundle` wraps the crate's JSON in a `SecretsBundle` whose `to_json()` gives it back and `free()` drops it, and `importSecretsBundle` sends `to_json()` and frees the bundle, as WASM consumes it. `getReceivedRoomKeyBundleData` hands out a `StoredRoomKeyBundleData` whose file key is hidden from `JSON.stringify` and `console.log`; `receiveRoomKeyBundle` sends its room, inviter and URL with the downloaded bytes as base64. `DehydratedDevices.create` holds nothing until `keysForUpload` (one `createDehydratedDevice` call, refused a second time on the same object), and `RehydratedDevice.free` drops the device the crate holds.
- The room key imports call matrix-js-sdk's progress listener once, when the import is done, with WASM's last arguments (`lastProgress`); WASM calls it once per key.
- `native/crypto/surface.json` marks each member the shim implements with `shimImpl: true`; `libs/native/crypto-backend/src/native/surface.spec.ts` fails when a marked member has no implementation, or a stand-in is not over its WASM class.

The SDK test bed starts the disposable homeserver and runs real matrix-js-sdk clients in Node: one on the shim with the crate's CLI as the bridge, the others on WASM, in both roles, and the same flows with every client on WASM as the control. It checks device key upload, an encrypted room that members join later, messages both ways, a rotated session, a message whose room key arrives after it, the encryption info a WASM receiver reports for the same event, a restart on the same store (and a wrong key that fails), a machine the crate dropped and the shim reloads, and a CLI that dies mid-session: the machine is lost, the sync stops, and a room key sent meanwhile reaches the client started again on the same store. `scripts/native-crypto-sdk-trust.e2e.mjs` runs the trust paths the same way, with the shim on one user's first device and on the other user's second device: cross-signing bootstrapped on both sides, the other user verified by signing their identity, local trust and blacklisting deciding who gets room keys, secret storage and a key backup, a second device that imports room keys (with progress), distrusts the backup until it imports cross-signing from secret storage, refuses a wrong backup key and restores with the right one, a restart that keeps cross-signing and the backup, an identity reset reported as a violation then withdrawn and pinned, and a device replaced under its ID whose stale read is refused (`StaleObject`, nothing trusted). `scripts/native-crypto-sdk-verification.e2e.mjs` runs interactive verification and the rest of the surface the same way, with the shim requesting in one orientation and answering in the other: self-verification with SAS (the new device then receives the cross-signing keys and the backup key) and with QR codes shown by the trusted and by the new device, another user verified with SAS and with a QR code in a DM, the phases each side reports, cancels by either side at every stage with code and reason, a mismatched SAS, the time limit counting down, two requests at once (both cancelled, as upstream does), a request that arrived while the shim client was stopped, a secrets bundle moved to a new device that then cross-signs itself and restores the backup, room history shared on invite (MSC4268) in both directions, and a dehydrated device made by the shim and rehydrated by new logins on both backends. matrix-js-sdk 45 reads a dehydrated device's events with the older `GET` form of MSC3814, which Tuwunel does not serve, so the bed's network turns it into the current `POST`. QR sign-in (MSC4108) needs a rendezvous server, so the bed moves the secrets bundle with the calls that flow makes. matrix-js-sdk has no non-interactive way to verify another user, so the bed calls `OtherUserIdentity.verify()` on the machine and sends the request through matrix-js-sdk. Its clients repair stale memberships as the app does (`stale-membership-repair.ts`): Tuwunel can send a `state_after` that lags the same response's timeline. It needs cargo and Docker: without either it is skipped and says why, and in CI it fails instead. CI runs it in the `Native crypto (Rust)` job.

For a flow that does not finish, `NATIVE_CRYPTO_TRACE=<file>` passes the shim's `trace` option (one line per batch, per poll's events and per mirror change, with method names, flow IDs and states only) and records each client's verification to-device traffic and matrix-js-sdk's phases; the verification bed appends the flow's trace to the file when a flow is stuck or a case fails. `NATIVE_CRYPTO_JITTER` and `NATIVE_CRYPTO_BRIDGE_JITTER` (milliseconds) add random delays around HTTP requests and after bridge answers, `NATIVE_CRYPTO_BED_LOAD` runs that many busy processes, and `NATIVE_CRYPTO_REPEAT=<n>` self-verifies n new devices in turn (`NATIVE_CRYPTO_REPEAT_FLOWS`: `sas`, `request`, `incoming`).

## Run it on Android {#android}

Every Android build packages `libtrinity_crypto.so` for the four ABIs the app ships, built by the Gradle task `buildNativeCrypto` (`native/crypto/build-android.sh`, cargo-ndk); [Android](../android/#native-crypto-toolchain) lists the toolchain and the Gradle properties. `-PtrinityNativeCrypto=false` (or `TRINITY_NATIVE_CRYPTO=0`) builds an app without it, which runs on WASM. The web bundle is the same either way: the app asks the plugin at run time.

### The plugin {#android-plugin}

`TrinityCrypto` (`android/app/src/main/java/dev/trinityproject/trinity/crypto`, registered by `MainActivity`) is the shim's bridge (`libs/platform-native/src/lib/native-crypto-host.ts`). It never echoes request or answer text in an error or a log line; a failure is a fixed message and a code.

| Method             | Arguments                                            | Resolves                                    | Rejects with                                                                                     |
| ------------------ | ---------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `available()`      | none                                                 | `{ available }`: whether the library loaded | never                                                                                            |
| `call(...)`        | `userId`, `deviceId`, `request` (one request's JSON) | `{ response }`, the crate's JSON answer     | `InvalidArguments`, `NotBuilt`, `QueueFull`, `KeyUnavailable`, `StoreUnavailable`, `NativeError` |
| `callBatch(...)`   | `userId`, `deviceId`, `requests` (a JSON array)      | `{ response }`, the answers in order        | the same                                                                                         |
| `deleteStore(...)` | `userId`, `deviceId`                                 | nothing, also when there was no store       | `InvalidArguments`, `QueueFull`, `StoreUnavailable`                                              |

- One background thread per machine (user and device), each with a queue of 64 calls; a full queue rejects with `QueueFull`. Never the main thread.
- The plugin opens the store: `getNoBackupFilesDir()/crypto/<sha256(userId)>/<sha256(deviceId)>`, and injects that path and the store key into every `init`, in place of any the request names. The crate's JNI entry takes the key as a byte array, the plugin wipes its copy after the call, and the crate refuses an `init` with no store (`StoreUnavailable`), so a machine never runs in memory. A request for another machine than the call's fails alone (`InvalidRequest`).
- The key is 32 random bytes made on the store's first `init`, kept only wrapped by AES-GCM under a non-exportable Android Keystore key (no user authentication, so a background sync can open it), bound to the device's path as associated data, in `store-key.wrapped` inside the store directory. An existing store without its key, or a key that does not unwrap, rejects with `KeyUnavailable`; a new key is never made for an existing store. `no_backup` is never backed up, and the manifest's backup and data extraction rules exclude all app data from cloud backup and device transfer; a Keystore key could not move anyway.
- `deleteStore` runs on the machine's thread: it closes the machine, then deletes the directory with the wrapped key. Sign-out, account removal, a sign-in on a new device, erase all data and the app lock erase call it for every account whose store is native.

### Which accounts are native {#android-accounts}

When the plugin reports available, a new sign-in's store is native and its session is saved with `cryptoBackend: 'native'`, and no JavaScript store key is made for it (`cryptoStoreKeyed` stays unset). The app installs the shim before the first account starts crypto, so every account of that process is native; elsewhere nothing is installed. A session opens only on the backend that made its store (`cryptoBackendFor` in `libs/util/matrix`): an unmarked session on a native build, or a marked one on a build without the library, fails as `crypto-backend-mismatch`, opens no store, and asks to sign in again on this build. There is no migration between the two kinds of store and none is planned: the mobile apps have no released users.

A lost machine (`onMachineLost`) stops that account's client and reports it like a failed background restore ("A background Account needs attention"); "Retry Account" starts it again, which reloads the machine from its store.

## The crypto backend facade {#facade}

`@matrix-org/matrix-sdk-crypto-wasm` resolves to `libs/native/crypto-backend`, everywhere: Trinity's libs, the E2E support code and matrix-js-sdk's own imports. An `overrides` entry in `pnpm-workspace.yaml` links the facade in place of the package, and the facade installs the real package under the alias `@matrix-org/matrix-sdk-crypto-wasm-real` and re-exports all of it with `export *` (ESM and types) or as the same `module.exports` object (CommonJS). This is where a native backend can later slot in under matrix-js-sdk.

Today it changes nothing: every export is the WASM package's own object, which `src/matrix-sdk-crypto-wasm.spec.ts` checks name by name, and the build serves the same `.wasm` file at `assets/crypto/matrix_sdk_crypto_wasm_bg.wasm`. Nx cannot see the override, so `libs/util/matrix` and `e2e/support` name the facade in `implicitDependencies`; every other project that loads the package reaches it through them, which `scripts/crypto-backend-dependents.spec.mjs` checks, so an edit to the facade re-runs their builds and tests. Code that needs the package's files rather than its exports, such as the build's asset rule, reads them from `libs/native/crypto-backend/node_modules/@matrix-org/matrix-sdk-crypto-wasm-real`.

## Keep the WASM pin {#pin}

The crate pins `matrix-sdk-crypto`, `matrix-sdk-common` and `matrix-sdk-sqlite` exactly to the release the WASM package in the root `package.json` is built on. `node scripts/native-crypto-pin.mjs`, also part of `pnpm nx test scripts`, fails when the WASM version, the pins, `Cargo.lock` or the snapshot `native/crypto/wasm-lock.json` disagree. On a WASM bump, download that release's `Cargo.lock`, refresh the snapshot with `node scripts/native-crypto-pin.mjs snapshot <Cargo.lock> <version> <commit>`, then move the pins and the lock to match.

The same check fails unless three versions are equal: the root `package.json`'s WASM version, the facade's `npm:` alias in `libs/native/crypto-backend/package.json`, and the exact version the installed matrix-js-sdk depends on. The override replaces matrix-js-sdk's own pin without a warning, so a matrix-js-sdk update that moves its pin would otherwise run on the old WASM. Renovate does not bump the three together: it never moves the WASM package, in either manifest, and the matrix-js-sdk update it opens changes only the SDK's pin. The pin check fails that update until whoever takes it moves both the root `package.json` version and the facade's alias to the SDK's new pin (and `native/crypto` with them, as above).

## Release isolation {#release-isolation}

`scripts/android-release-isolation.mjs` checks a release APK or AAB: with native crypto (the default) the library for every ABI the package ships native code for and the `TrinityCrypto` plugin, without it (`TRINITY_NATIVE_CRYPTO=0`, or `--native-crypto=off`) no library at all, and in both modes no debug-only crypto code (the retired `TrinityCryptoDebug` plugin). `pnpm android:build:release` runs it, and CI's `Android release build` job runs it in both modes on every pull request that builds the app. CI cross-builds the libraries once per run in `Native crypto (Android libraries)`, cached by the crate's sources, and every Android job packages them.

## What milestone 3 needs {#milestone-3}

Milestone 3 puts a JavaScript shim between matrix-js-sdk and the crate. The manifest's notes and `shimNotes` say what the shim does for each member; these are the obligations a wrong shim would break silently. `pnpm nx test scripts` fails when a `shimNotes` member, or a member whose note says "the shim must", is not named here.

- Bridge batches stay at or under 1 MB.
- Store: refuse `StoreHandle.open` with a store prefix. WASM then opens a passphrase store, or an unencrypted persistent one when Trinity has no storage key; the crate offers only a raw-key store or memory.
- Stale objects: pass the key from the snapshot its JavaScript object wraps. `ed25519Key` goes to `Device.setLocalTrust`, `Device.verify`, `Device.encryptToDeviceEvent` and `Device.requestVerification`. `masterKey` (the public master key) goes to `OwnUserIdentity.verify`, `OwnUserIdentity.withdrawVerification`, `OtherUserIdentity.withdrawVerification`, `OtherUserIdentity.pinCurrentMasterKey`, `OwnUserIdentity.requestVerification`, `OtherUserIdentity.requestVerification` and `OtherUserIdentity.verificationRequestContent`. Without it the call acts on whatever device or identity now has that ID; with it a changed object fails with `StaleObject`, and nothing changes, is encrypted or is requested.
- Trust: ask `OlmMachine.getDevice` / `OlmMachine.getIdentity` again for each trust question (a snapshot is current only when returned), and build real `OwnUserIdentity` and `OtherUserIdentity` instances from the snapshot's `kind`, because matrix-js-sdk uses `instanceof`. After a stand-in's own trust change, read it again before the call resolves, as WASM's object shows that change. Code that holds a `Device` or identity must read it again after `devicesUpdated` or `userIdentityUpdated`: neither backend's object sees a change made by a sync.
- Sharing strategy: map `CollectStrategy.deviceBasedStrategy` (`onlyAllowTrustedDevices`, `errorOnVerifiedUserProblem`) in WASM's order (`onlyTrustedDevices`, else `errorOnUnverifiedUserProblem`, else `allDevices`) and `CollectStrategy.identityBasedStrategy` to its own name. A wrong mapping shares room keys with unverified devices.
- Verification: pass the decimals it displayed to `Sas.confirm` (the crate requires them), so a SAS replaced under the same flow ID fails with `StaleObject` instead of being confirmed. Map `UnknownVerification` from `VerificationRequest.cancel`, `VerificationRequest.acceptWithMethods`, `Sas.cancel`, `Sas.cancelWithCode` and `Qr.cancel` on a flow it saw done or cancelled to WASM's "no request". Answer `VerificationRequest.timeRemainingMillis` as `max(0, expiresAtMs - Date.now())`, treat `timedOut` as true at the snapshot's time only, keep its mirrors from the `verificationRequestChanged` and `verificationChanged` events, read `qrCodeBytes` only when matrix-js-sdk asks for the bytes, and build real `Sas` and `Qr` instances by `kind` for `VerificationRequest.getVerification`.
- Android plugin (slice 6): never echo request or answer text in its own error strings or logs, as the shim does not; report a fixed message and a code.
- Lost machine: when the shim calls `onMachineLost`, the host must stop the client. The shim keeps that machine's sync input pending so matrix-js-sdk does not move past to-device events it never processed; a host that keeps the client running syncs nothing more on it.
- Events: poll `pollEvents` after every call or batch (`OlmMachine.registerRoomKeyUpdatedCallback` and the other callbacks), and on a non-zero `dropped` treat the view as stale (retry undecryptable events). Call the secret callback (`OlmMachine.registerReceiveSecretCallback`) with the name from `secretReceived` and no value: matrix-js-sdk ignores the value and reads `getSecretsFromInbox`.
- Secrets: a decrypted `m.secret.send` or secret push in the answer of `OlmMachine.receiveSyncChanges` or `OlmMachine.receiveSyncChangesMsc4186` comes without `content.secret`, unlike WASM's (matrix-js-sdk passes the event to the app); the shim must not put it back. Turn the `SecretsBundle` object back into JSON with `to_json()` for `OlmMachine.importSecretsBundle`, and wrap the JSON of `OlmMachine.exportSecretsBundle` in an object whose `to_json()` returns it. Wrap the `decryptionKeyBase64` of `getBackupKeys` with `BackupDecryptionKey.fromBase64` for `BackupKeys.decryptionKey`.
- Import progress: replay the progress listeners of `OlmMachine.importExportedRoomKeys` and `OlmMachine.importBackedUpRoomKeys` from `lastProgress`, as WASM's last listener call.
- Machine state: set `OlmMachine.roomKeyRequestsEnabled` again after every `init` (the crate keeps it in memory only, as upstream). Call `OlmMachine.encryptStateEvent` only after the room key is shared, as matrix-js-sdk does: without one upstream panics, and the crate drops the machine.
- Room key bundles: pass `roomId`, `senderUser` (as `inviter`) and `url` from the bundle data object it was handed, and the downloaded bytes as base64, to `OlmMachine.receiveRoomKeyBundle` (a newer bundle fails with `StaleObject`).
- Dehydrated devices: defer `DehydratedDevices.create` to `keysForUpload`, which is one native call (`createDehydratedDevice`), and refuse a second `keysForUpload` on the same object. Call `dropRehydratedDevice` for `RehydratedDevice.free`.
- libolm: throw "legacy libolm migration is not supported on native" from `Migration.migrateBaseData`, `Migration.migrateOlmSessions` and `Migration.migrateMegolmSessions`.

## Before a release build may use it {#before-release}

Done in milestone 3: native code builds the store path and the store key comes from the Android Keystore, neither from JavaScript; the plugin is registered in `main`; each machine's queue is bounded; and the obligations in [What milestone 3 needs](#milestone-3) are in place. Still open:

- QR sign-in (`importLinkedSecrets` in `libs/data-access/auth`, `auth.service.ts`) is tried on the emulator: the SDK test bed covers its secrets bundle calls, not the rendezvous.
- A verification in progress when the crate drops the machine ends there: the reloaded machine has none, the registry is emptied, and matrix-js-sdk's request objects see no further change. The user starts again.
- A stuck native call holds up only its own machine on Android (one thread per machine). The CLI bridge still runs one call at a time.
- iOS needs its own plugin with the same interface as [the Android plugin](#android-plugin) (Keychain in place of the Keystore).
- matrix-js-sdk 45 reads a dehydrated device's events with the older `GET` form of MSC3814, which Tuwunel does not serve, and loops on rehydration there, on either backend: the SDK test bed rewrites the request, the app does not yet.
- A verification that occasionally never finished in the SDK test bed, with the shim device requesting, seen twice in about a dozen full runs and not reproduced since in several hundred flows under load and slid timing. The bed's diagnostics (below) dump the trace if it comes back.
- The batch time limits are checked on a real phone (slice 6), with suspend in mind: a timer that fires on resume would count a suspended bridge call as stuck and lose a healthy machine.
- A lost machine's to-device events are delivered after a restart from a saved sync token, tested on the emulator with the app's own store (slice 7). The SDK test bed proves only a restart without a token: matrix-js-sdk's persistent store needs IndexedDB, which Node lacks without a new dependency. The reasoning: the IndexedDB store persists the token in `setSyncData`, which runs after a sync is processed, and a lost machine's sync is never processed, so the saved token is the one before it and the server still holds those events.
