End-to-end encryption spans account lifecycle, SDK persistence, secret storage, recovery, and device verification. Trinity keeps those responsibilities separated so a UI flow cannot accidentally take ownership of cryptographic state.

## Device-scoped crypto storage {#crypto-storage}

Rust crypto storage belongs to a Matrix user and device. New-device login receives a device-scoped prefix of the form `trinity-crypto:${userId}:${deviceId}`; same-device reauthentication can reuse the recorded prefix. Store teardown must use the prefix captured by the Account rather than reconstructing it from current UI state.

The SDK's crypto database naming logic is centralized in `libs/util/matrix`. Do not duplicate suffixes or call broad store-clearing APIs without the corresponding account-owned prefix.

Each new store is encrypted at rest with its own random 32-byte store key, passed as `initRustCrypto({ storageKey })`. The key is created when an account binds a new device-scoped store, kept in secure storage under `matrix.cryptoStoreKey:<cryptoPrefix>`, and deleted with the store: on sign-out, hard logout, the orphan sweep and installation reset. The account record carries a non-secret `cryptoStoreKeyed` flag. Electron, Android and iOS keep the key in the OS keychain or keystore. The web has none, so there the key is wrapped with a non-extractable AES-GCM key held in IndexedDB. That keeps the raw key out of script-readable storage, and deleting the wrapping key makes the store unreadable. It does not help against someone who can read the whole browser profile from disk, and script running in the app's origin can still ask WebCrypto to unwrap the key.

A keyed store is never opened without its key, and secure storage reads tell three cases apart: present, absent, and unavailable. Unavailable means the OS keychain cannot be reached right now, for example a keyring that is not unlocked yet, a denied keychain, or a desktop that fell back to web storage for the session. Only an absent key is lost; this happens, for example, after a restore onto a new phone or a wiped keychain. A lost key fails the start as `crypto-store-key-lost` and asks the user to sign in again. That re-authentication signs in as a new device, which gets a new store and key while the old store is reclaimed; once the new session is saved and started, the replaced device is signed out on the server, best-effort, with its old token. That sign-out is skipped when the new session's first start fails. An unavailable key fails as `secure-storage-unavailable`. Startup offers a retry once the keychain is unlocked, and also, behind a confirmation, removing the account, for a keychain that will not come back. It never replaces or deletes the store on its own.

A store created before store keys existed stays unencrypted. The crypto WASM refuses to open such a store with a key and cannot encrypt it in place, so a key is never added to an existing store. Security settings asks the user to sign out and back in on that device. Once key backup is on for the account, so the new device can restore its history, the rooms shell also shows a "Sign in again" banner in the global banner slot, below the encryption prompt and above a limited-capability notice. It can be dismissed for the session. Key backup being on does not prove the person still has the recovery key, so "Sign in again" first confirms that reading older messages afterwards needs the recovery key or another signed-in device. Its sign-in is a re-authentication that always asks for a new device (`/login?reauth=<userId>&device=new`), because a same-device re-authentication keeps the existing store: saving the new device creates a new, encrypted store and key, deletes the old store, and signs the old device out once the new session has started. Nothing migrates an account on its own.

## Secrets stay behind storage adapters {#secret-storage}

The host selects the strongest available credential backend. Web storage is origin-local but script-readable. Electron uses only a usable OS encryption backend: on Linux it refuses `basic_text` and `unknown`. Without one, secrets fall back to the same script-readable storage as the web, unprotected on disk, and `SecureStorageService.withoutKeychain()` reports it. Before a sign-in stores anything, Account Runtime asks the person, through `UNPROTECTED_STORAGE_CONSENT`, whether to store the account that way; declining cancels the sign-in and stores nothing. A sign-in that created a new device signs that session out again, also when the question goes unanswered or the stored answer cannot be read; a re-authentication on the stored device keeps that device and stores nothing new. Sign-in asks the same question again before Account Runtime does, so the session can be handed back. The answer is kept per device (`trinity.secure-storage.unprotected`), so it is asked once. Security settings warns, and an account stored that way before the question existed also gets a one-time notice at the next start, whenever secrets actually sit in that storage (`storesUnprotectedSecrets()`), not whenever this launch lacks a keyring. A launch whose keychain works again moves those leftovers into it, crypto store keys unwrapped, and deletes each one only after the keychain took it. A value the keychain already holds wins and the leftover beside it is dropped, and so is a store key that can never be unwrapped. A declined registration signs its new session out too, since the account then exists only on the server. Capacitor uses its native secure-storage adapter without cloud synchronization, and on iOS with the this-device-only keychain class, so a backup restored onto another device does not bring the secrets along. An item written before that class was set is moved to it in place at every launch (`AppDelegate`, `SecItemUpdate` on items still in the plain when-unlocked class), so nothing has to be written again. iOS also keeps the rest of the app's data out of iCloud and computer backups: the web view's `Library/WebKit` (IndexedDB and localStorage, including the crypto and sync stores), `Library/NoCloud`, where composer drafts live on iOS instead of Capacitor Preferences (drafts saved in Preferences move there once), and the App Group `push-handoff/` directory with room and contact names. Backups taken before this change still hold that data. Android excludes the app's data from cloud backup and device-to-device transfer. If a native backend is unavailable, the capability reports that state rather than pretending plaintext storage is secure.

Diagnostics contain stable codes and recovery information only. Never include access tokens, recovery keys, private message content, preference values, raw server bodies, account identifiers, or unfiltered exception text.

## Trust is a capability {#trust-capability}

The Trust data-access library owns encryption health, device lists, cross-signing repair, recovery reset, and verification commands. Feature pages present those states and actions. They do not keep a second trust model or call SDK crypto methods directly.

Verification and recovery actions are finite Observables, while trust health is projected state. Preserve cancellation and account boundaries when a dialog or routed page closes.

## Setup never replaces an existing identity {#identity-preservation}

Trust reads one status per Account with `readTrustSnapshot`: `ready`; `needs-recovery` when secret storage exists but this device has not unlocked it; `needs-verification` when the Account has a cross-signing identity that another device published, no secret storage, and this device neither holds the private keys nor is verified; and `needs-setup` otherwise: no identity, this device holds it and only recovery is missing, or this device is verified but the private keys stay on the device that published the identity. That last case is `TrustService.recoverySetupElsewhere`: the banner and Security settings point the user to the device where encryption was first set up instead of offering setup. First-device setup is offered only for `needs-setup` without an identity held elsewhere. Private keys on this device count as the identity only when the published identity verifies against them (`isCrossSigningReady`): a reset cancelled before its upload leaves a full set of keys nobody published, and setting up recovery from those would store keys that can never verify a device.

`TrustService.setUp` also refuses an Account whose identity lives elsewhere. It first re-reads the Account's published identity from the homeserver (`userHasCrossSigningKeys(undefined, true)`, which refreshes the device's copy and drops private keys that don't match it), then checks the keys this device holds against that identity, all before bootstrapping, because `bootstrapCrossSigning` with no private keys available creates new keys and replaces the identity, which cuts the user's other devices out of every MSC4153 strict sender's recipients. For the Account's own user that call answers from the device's refreshed copy, so an identity this device created but never uploaded (a first setup whose upload was cancelled at the password prompt or failed) still reads as present. Setup therefore also asks the homeserver for the published master key (`/keys/query`, `readPublishedMasterKey`). When this device holds an identity's private keys but the server has no master key, setup bootstraps with `setupNewCrossSigning: true` and uploads new keys: there is nothing on the server to replace, and without it `bootstrapCrossSigning` would keep the unpublished keys and secret storage would store them. If the device holds no keys there, its two reads disagree, and setup refuses rather than create keys over an identity the server may still have. Setup also refuses when the server's master key isn't the one this device holds. Both reads fail closed, and the refusal links to Security settings, where verifying and resetting live. Resetting the identity remains a separate, explicitly confirmed action. It lives in Security settings, never in the room banner, which cannot be dismissed; for an Account without secret storage the reset page asks for no recovery key. For someone without the device that holds the identity, the verify dialog the banner opens is the way there: in `needs-verification`, while this device's own request is unanswered or has stopped, it offers "Open Security settings". The trust capability cannot open Settings itself, so the modal closes with `MANAGE_IDENTITY` (a `TrustDialogResult` from `@trinity/data-access/trust`) and the application-surface presenter maps it to Security settings. The presenter offers the button only where closing lands there: from the top level it opens Settings at Security, and over Settings › Security (the dialog or the routed page) closing returns there; over any other Settings section the button is not shown. The routed page navigates to `/settings/security`.

## Decryption failures say why {#decryption-failures}

Conversations maps `MatrixEvent.decryptionFailureReason` to an `UndecryptableReason` while it normalises the event, and Message Presentation gives each reason its own text and a `deviceFixable` flag. Two reasons are fixable on this device: a key withheld because this device was unverified when the message was sent, and history this device cannot read until it unlocks key backup. For those rows the Rooms feature's `UndecryptableFixService` derives one button from Trust's live status: "Verify this device" on an unverified device (the recovery-key flow when the account has recovery, verification with another device when its identity has none, encryption setup when it has no identity), "Use recovery key" on a verified device that still needs recovery, and "Security settings" when the identity's keys are on another device. The button follows the status and disappears when nothing on this device can help; read-only rows never show it. Keys withheld while the device was unverified are not sent again, so those rows stay unreadable after verifying. Messages from devices their owner never cross-signed, and from senders whose identity changed after you verified them, have their own texts, but the SDK reports neither in Trinity's all-devices mode: it decrypts every message regardless of trust (`TrustRequirement.Untrusted`), so those reasons appear only once strict mode exists. Every other code keeps the generic "Unable to decrypt this message", as do edit history and the room-list preview. When unlocking succeeds, the key-backup downloader fetches the sessions it queued, so history becomes readable without a reload. On restart the SDK decrypts cached events again, so a reason can change after a reload, and that reload is the only retry for events rejected for trust reasons.

## Every signed-in account shows its trust {#account-trust}

Background accounts keep syncing, so an unverified device of a background account can stop receiving room keys from MSC4153 strict senders with nothing on screen. `TrustAccountStatusService` reads every live account through `TrustCryptoPort.liveAccountIds` and `forAccount`, recomputes an account's summary with `readTrustSnapshot` whenever that account's crypto state changes (a burst of changes within one microtask starts one read, and a read that a newer one overtakes still runs but its result is dropped), and exposes a read-only map of account id to `verified`, `unverified`, `not-set-up` or `unknown`. Application Runtime owns its lifetime for the session. The account switcher, the "Accounts in view" picker and submenu, and Settings › Server show an "Unverified" mark on an account whose identity exists but whose device here is not verified; the mark's text is part of the row's accessible name, and in Settings › Server part of the account's heading and of its block's name. Each row and block also carries the status in `data-trust` for browser journeys. A verified device counts as verified even when recovery has to be set up on another device. Accounts with no identity, and accounts whose status is not known yet (crypto still starting, or a failed read), carry no mark: the setup banner covers the first, and nothing is claimed about the second. A soft-logged-out account has no live client and is not listed.

## New devices are verified before use {#device-verification}

When a sign-in creates a device this installation has not used for the account (no saved record, or one with a different device id, for password, SSO and OIDC sign-ins alike), Accounts publishes it on `AccountRuntimeService.newDevices` once the sign-in's record is saved, so before the sign-in page receives the outcome and whatever that outcome is: a sign-in that fails or is cancelled after the save still publishes it, since the next launch would restore the saved record as an existing device. A re-authentication that keeps the saved device id is never new, and a saved record that cannot be read proves nothing. Auth's own `isNew` answers a different question (whether a refused sign-in's session may be revoked) and stays as it is. Trust records the device id in an account-scoped device preference (`trinity.trust.device-confirmation`, excluded from config export), so closing or reloading the app does not skip the check, and derives the gate for the active account: required while the device is unverified and the account has an identity (`needs-recovery`, `needs-verification`, or `needs-setup` while the homeserver publishes a master key, asked once per new device with `readPublishedMasterKey`, once its session is live), pending while that is not known, and not required otherwise. When the homeserver publishes no master key the record is dropped at once: a device that signed in before any identity existed counts as an existing device and is never sent to the check, even if an identity is set up elsewhere later; it keeps the banner. A server that cannot be asked proves nothing, so the record stays and the gate follows this device's own read: not required while it says `needs-setup`, required once the device's own identity download shows the identity. A record that cannot be read counts as none, so the check never traps someone it cannot help. Otherwise the record is cleared when a fresh read on that account shows the device verified, or by the debug-build skip.

`deviceConfirmationGuard` runs after `authGuard` and the Back guard on Rooms and on every Settings section except Security. Every guarded navigation waits while the gate is pending, for up to `DEVICE_CONFIRMATION_SETTLE_MS` (10 seconds), and then lets the route through. It confirms a `required` gate with `confirmRequired()`, a fresh read of that exact account, because just after an account switch the gate can still reflect the previous account's status; that read has the same 10-second limit, and a failed or late read lets the route through too.

The session's `DeviceConfirmationCoordinator` records Accounts' facts in Trust, loads the active account's record, clears it once the device is verified, and redirects Rooms and Settings to the check when the gate turns required later. It confirms with the same fresh read, started only while Rooms or Settings is open, and each change cancels a read still in flight, so a stale answer never redirects. It closes any other dialog over the app first; while a recovery dialog or a verification of the account's own devices is open, it waits for that flow to end and redirects only if the check is still required.

`/encryption/confirm` re-implements no flow: the recovery key, the confirmed reset and verification with another device go to the existing unlock and verify pages with a return address, and the verify page's "Open Security settings" reaches Security. "Remove account from this device" runs the same flow as the account menu: Application Runtime's `AccountRemovalLauncherAdapter`, reached through `ACCOUNT_REMOVAL_LAUNCHER` in `@trinity/platform-native` because the Crypto feature may import neither Accounts nor an application library. That flow shows its own messages and goes to sign-in itself, so they survive the screen leaving when the sign-out ends the check; the screen waits for the removal's outcome before it navigates. When another account is signed in, "Use another account" switches to the first one in the account switcher's order and opens Rooms for it, through `ACCOUNT_SWITCH_LAUNCHER` (Application Runtime's `AccountSwitchLauncherAdapter`), so a pending check on one account never blocks the others. While the status loads the screen shows "Checking this device…"; whenever it stays loading for the settle time, the screen offers "Try again", "Continue" (which opens Rooms, as the guard does after its own wait), "Remove account from this device" and, with another account signed in, "Use another account". As soon as nothing is required the screen replaces itself with `/rooms`, where the existing banner keeps prompting on an account without recovery. Debug builds (`environment.production` false) also offer "Skip for now (debug build)"; release builds never do. Existing devices and accounts without an identity are never sent to the check. None of this changes the device isolation mode: Trinity still uses `AllDevicesIsolationMode(false)`.

Trust also keeps an account-scoped device preference, `trinity.trust.slot-forecast` (excluded from config export), that records which encryption prompt this device last needed for the Account: `none`, `needs-setup`, `needs-recovery`, `needs-verification` or `setup-elsewhere`. `TrustSlotForecastService` writes it whenever a coherent status arrives for the active Account. Like the other account-scoped device preferences, it stays on the device after the Account is removed; deleting the Account or an installation reset removes it. `deviceConfirmationGuard` reads it before Rooms opens, waiting at most `FORECAST_HYDRATE_MS` (300 ms) and failing open, and an Account switch reads it too. While the live status is unknown, `CapabilityStatusService` decides the global banner slot from the forecast with the live priority rules, and the encryption banner lays that prompt out hidden (`visibility: hidden`, `aria-hidden`, `inert`, and nothing in its live region) until the live status confirms it and the same banner is revealed in place. Only the stored forecast is used, and only while the status is still unavailable, as at start-up: a stale snapshot (a read that failed mid-session) forecasts nothing, so the trust failure notice shows as before. The forecast holds while the status is loading, up to the backstop below, and is dropped at once when Trust reports a failure (a `trust:projection` problem, even a dismissed one), so the failure notice takes the slot. A backstop drops it after `FORECAST_HOLD_MS` (10 seconds) if the status neither arrives nor fails. The forecast only sizes the slot: no Trust decision, flow or gate reads it. Separately, while a pointer is pressed `CapabilityStatusService` holds the slot and the prompt it holds together, and applies any change on release, so no banner swaps in or out, and the encryption prompt never changes kind or size, under a tap in flight. The encryption banner renders only that held prompt (`bannerPrompt` on `WORKSPACE_SYSTEM_STATUS`), never the live status. A held prompt the live status no longer supports, such as a shown prompt whose status turns `ready`, becomes a hidden, inert placeholder of the same kind until release, so nothing stale stays visible, announced or actionable.

## Photos and videos leave without identifying metadata {#media-metadata}

Encryption hides an attachment from the homeserver, not from the people in the room. Before an image is uploaded, its identifying metadata is removed without re-encoding it. Media data access does this for message attachments and profile photos, and Room administration uses Media's `withoutImageMetadata` helper for room photos. It removes Exif with its GPS location, camera make and model, capture time and serial numbers; XMP; IPTC; comments and text chunks; and anything appended after a JPEG's first image, such as Motion Photo videos and MPF secondary images. This covers JPEG, PNG, WebP and HEIF/AVIF. GIFs lose their comment and application extensions (XMP included) and keep loop control, colour profile and every frame. In TIFFs the identifying values are zeroed in place, so no offset moves: camera, software, author, document and page name, time, XMP, IPTC, Photoshop and Windows XP tags; the Exif IFD's serial numbers, unique ID, capture times and offsets, image history and MakerNote; and the whole GPS IFD. A TIFF-based camera raw (a DNGVersion tag, or a raw file name or MIME type such as `.nef` or `image/x-adobe-dng`) loses only its GPS IFD, because raw converters decode with its camera tags and MakerNote. Its XMP, which can repeat the location, is kept too. SVGs lose `<metadata>`, comments and editor namespaces (Inkscape, Sodipodi, Adobe, Sketch, RDF, Dublin Core) but keep `<title>` and `<desc>`; they are parsed with the platform XML parser and serialized again, and they are not sanitized: scripts stay as they are. A rotated or mirrored photo keeps an Exif block holding only its orientation, so it still displays the right way up. In encrypted rooms stripping runs on the plaintext, before encryption.

Message attachments that are MP4, MOV or 3GP movies, whether sent as videos or as files, lose their capture location and device identity the same way. Only the `moov` box is edited, in place: location atoms (`©xyz`, `loci`), device and software atoms (`©mak`, `©mod`, `©swr`) and XMP become `free` boxes of the same size, and the values of Apple's `keys`/`ilst` items for location, make, model, lens model, software, serial numbers and device ids are zeroed. No box moves, so chunk offsets stay valid and nothing is re-encoded. The capture date, encoder name and frame rate are kept. A movie is never loaded whole: unencrypted uploads read only the top-level box headers and `moov` (up to 64 MiB) and send slices of the original file around the patched `moov`; encrypted uploads, which read the whole plaintext anyway, are patched in that buffer. A thumbnail supplied by the native camera with a capture goes through the same image stripping before it is uploaded; a thumbnail rendered on a canvas carries no metadata.

Video stripping has known limits. These are uploaded as they are:

- location written into the samples by timed metadata tracks, such as iPhone `mebx` tracks, GoPro GPMF or DJI telemetry;
- boxes outside `moov`, such as a top-level XMP `uuid` box, and vendor data after `mdat`, such as Samsung's trailer;
- iTunes freeform `----` items in `ilst`;
- vendor `udta` atoms that are not removed: Canon's `CMT1`–`CMT4` (Exif blocks that can hold GPS), and GoPro's `GPMF` (telemetry) and `CAME` (camera serial number);
- compressed movies whose metadata is inside a `cmov` box, which are left unchanged as a whole;
- fragmented MP4 (`moof`, or `mvex` in `moov`), which is left unchanged as a whole.

Apple `keys` items that are stripped stay listed, with zeroed values.

The pure byte-level parsers live in `libs/data-access/media/src/lib/image-metadata`. An Exif block that cannot be read inside an otherwise sound file is dropped whole, orientation included. Stripping never blocks a send: a file whose container cannot be parsed with certainty, a BigTIFF, an SVG that is not UTF-8, is over 16 MiB or has an element with more than 1,024 attributes, a fragmented movie, a movie with a `moov` over 64 MiB, and every other format (WebM, documents), is uploaded unchanged, with whatever metadata it carries. A raw file is only recognised by its DNGVersion tag, name or MIME type, so a raw sent as a nameless blob with an empty type and no DNGVersion gets the full TIFF blanking.

Settings → Privacy → **Keep photo and video metadata** (off by default, stored per device under the older key `trinity.privacy.keep-photo-metadata`) lets a person send message attachments with their metadata. Conversations reads the choice when a send starts and passes it to Media Pipeline as the transfer's `imageMetadata` policy; with `'keep'` a photo or video is uploaded byte for byte, in plaintext and encrypted rooms alike, never partially stripped. A thumbnail supplied by the native camera is still stripped, since it is a derived preview rather than the person's file. Profile and room photos ignore the setting and are always stripped, because they are public and persistent.

## Logout and reset are ordered cleanup {#cleanup-order}

Sign-out targets an explicit account. Soft logout preserves recovery-critical local stores for reauthentication; hard logout requests their cleanup. An OAuth account's refused refresh or rejected token is always a soft logout, on every platform: its keys stay on the device until the person signs in again or removes the account. Installation reset gathers the identifiers needed for cleanup before deleting registries and preferences, then clears clients, SDK stores, host secrets, caches, and service workers through bounded operations.

Deleting an account (Settings › Account › Delete account) ends with a server-gone variant of the same removal, `removeDeletedAccount`, serialized as the `deleting-account` lifecycle operation. The homeserver has already deleted the account's devices, pushers and tokens, so it skips the pusher removal and `logout(true)`, which would only fail with `M_UNKNOWN_TOKEN`; it still forgets the push handoff entry, stops the client, deletes its stores, drafts and registry entry, and repoints the active account. Unlike ordinary removal, it also forgets the account's account- and conversation-scoped device preferences, because that Matrix ID can never sign in again. While `/account/deactivate` is in flight, `MatrixClientService.holdServerLogout` keeps a revoked token from triggering the hard-logout wipe, so the deletion cleanup owns what follows. On a server that uses OAuth 2.0, the provider's page deletes the account; Trinity holds the wipe for that account for the session and removes it the same way once its token stops working. Holds still apply to OAuth accounts, and a released hold lands soft.

Cleanup can be partial or uncertain when another tab or process holds a database. Surface that typed outcome; do not report success merely because observation reached its timeout.
