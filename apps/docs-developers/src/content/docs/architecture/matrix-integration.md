Trinity uses `matrix-js-sdk` as the authoritative source for Matrix protocol state. SDK construction and direct SDK access live in data-access libraries, principally Matrix Client and the capability adapters built over it.

## One client per live account {#client-registry}

The `AccountRuntimeService` restores saved accounts and coordinates the active account. The Matrix client registry owns live client instances and their sync lifecycle. Capability code resolves the client for an explicit account or follows the selected-account projection appropriate to its scope.

Never use the active account implicitly for work that already has an account identifier. Room and event identifiers alone do not establish which authenticated client owns an operation.

## Adapt SDK state at the boundary {#adapt-sdk-state}

Data-access services translate SDK objects and events into stable Trinity read models and commands. Feature and component code consumes those public models; it does not expose SDK objects through UI APIs or attach competing SDK listeners.

For active-client projections, the shared `projectFromClient` adapter coordinates client replacement, event attachment, burst coalescing, reconciliation, and reset. `projectActiveAccount` (`libs/data-access/matrix-client`) is the SDK-free counterpart of `projectFromClient`: it holds an engine subscription for the Active Account under a `ProjectionRuntime` lease, coalesces bursts, and resets and subscribes again on an account switch or a new session generation. Other scopes use their matching owned projection lifetime.

## Engine interfaces {#engine-interfaces}

Each data-access capability reaches Matrix through an engine interface, so another engine can implement it later ([#1153](https://github.com/quwisky/trinity-matrix-client/issues/1153)). The `matrix-js-sdk` adapter for a capability lives in its `js-sdk/` folder; only those folders reach the SDK. Reach means importing `matrix-js-sdk`; importing `ConnectionError`, `HTTPError` or `MatrixError` from `@trinity/util/matrix`, which re-exports those SDK classes; calling `clientFor` or `detachedClient`, reading `matrix.instance`, or indexing `MatrixClientService['clientFor' | 'instance' | 'all' | 'detachedClient']`; and calling `.all()` in a file that references `MatrixClientService`. Specs and `*.spec-harness.ts` files do not count. `architecture/engine-boundary-allowlist.json` lists the files that still reach the SDK. It only shrinks: a new offender and a stale entry both fail `scripts/engine-boundary.spec.mjs`.

Values crossing an engine interface are plain data: strings, numbers, booleans, `null`, arrays, and plain objects. No `undefined`, `Date`, `Map`, `Set`, class instances, or functions.

A command is a cold observable that emits one result and completes. Expected failures arrive as `{ ok: false, failure }` with an `EngineFailure`: a `kind`, a `code` (`EngineFailureCode`), privacy-safe `diagnostic` metadata and plain-data `params` typed per code, never text. TypeScript owns the copy: `engineFailureMessage` in `@trinity/util/matrix` is the one table that turns a failure into user-facing words, so a Rust engine returns the same codes. Only unexpected faults error the stream. A subscription emits a snapshot first and changes after it, except a feed, which has no snapshot and replays nothing: it emits only what happens while it is subscribed (`recordFeed` checks that shape). Media never crosses as bytes: commands return a URL the webview can load, and uploads take a Blob or File handle. Synchronization stays authoritative: a command's result does not replace the state that sync reconciles.

### Session engine {#session-engine}

`SessionEngine` (`libs/data-access/matrix-client`) exposes the live accounts as plain data. `session()` emits a `SessionSnapshot` (active account, per-account status, soft-logged-out ids) and every change after it. Access tokens never enter the snapshot: `accessToken(accountId)` is a separate stream, which carries the token's homeserver URL, expiry and whether it can be refreshed. Lifecycle commands are cold, and every lifecycle command's effect is in the next `session()` snapshot before it replies. `signOutAll` revokes the tokens and leaves the accounts live until `stop()`. `logoutRemote` ends one live session and `logoutSession` ends a stored one without starting it. `liveCredentials` reads a live session's own tokens once, so sign-out can still end that session after its client is gone. `deactivateAccount` takes user-interactive authentication as data: it answers `uia-required` with the challenge, and the pure `driveUia` loop sends it again with `auth`. `holdServerLogout` holds back the hard-logout wipe while subscribed and reports `token-died` before the result of any request that met the dead token; `releaseServerLogoutHold` ends the hold. `SESSION_ENGINE` provides the `matrix-js-sdk` adapter.

| `SessionSyncState` | js-sdk state                                       | Rust `SyncService` state    |
| ------------------ | -------------------------------------------------- | --------------------------- |
| `starting`         | none yet (live client before its first transition) | Idle (or `stopped`)         |
| `prepared`         | Prepared                                           | room list loaded from cache |
| `syncing`          | Syncing                                            | Running                     |
| `catchup`          | Catchup                                            | unused                      |
| `reconnecting`     | Reconnecting                                       | Offline                     |
| `error`            | Error                                              | Error                       |
| `stopped`          | Stopped                                            | Terminated (or Idle)        |

Plain-data readers use `SessionStateService`, which turns the snapshot into signals. Capability adapters still get SDK clients through `JS_SDK_CLIENTS` or `MatrixClientService` until their slice moves them to an engine. `architecture/session-facade-allowlist.json` lists the files that still import `MatrixClientService`; it only shrinks, and `scripts/session-facade.spec.mjs` fails on a new caller and on a stale entry. Removal is tracked in [#1153](https://github.com/quwisky/trinity-matrix-client/issues/1153).

### Room list engine {#room-list-engine}

`RoomListEngine` (`libs/data-access/room-library`) exposes an account's joined, invited and knocked rooms as plain `RoomInfo` rows. Its streams take an account id and emit a snapshot first: `rooms()` emits `VectorDiff` batches that start with a `reset`, while `typing()` and `directMap()` emit whole maps. `RoomListStore` holds one subscription per live account, and `ROOM_LIST_ENGINE` provides the `matrix-js-sdk` adapter.

Creating a room, space or DM, joining, leaving and tagging show their effect in `rooms()`, open subscriptions included, before the command replies; writing a space child link, or creating a room inside a space, shows in `spaceChildLinks()` the same way. `spaceHierarchy()` reads a space and its direct children from `/hierarchy`, page by page, and fails rather than loop when the server repeats a page token. Marking a room unread or read writes account data, which shows once `/sync` returns it. Every command on an account that is not live returns `account-not-live`. One contract, `defineRoomListEngineContract`, runs against `FakeRoomListEngine` in unit tests and against Synapse in `trinity-e2e-engine:contract`.

| Stream                                | Emits                                                         |
| ------------------------------------- | ------------------------------------------------------------- |
| `rooms(accountId)`                    | `VectorDiff<RoomInfo>` batches, a `reset` first               |
| `typing(accountId)`                   | joined room id to the members typing in it, own user included |
| `directMap(accountId)`                | the account's `m.direct` map, left rooms included             |
| `spaceChildLinks(accountId, spaceId)` | the space's live `m.space.child` links in spec order          |

### Timeline engine {#timeline-engine}

`TimelineEngine` (`libs/data-access/timeline`) exposes one room's timeline as plain `TimelineItem`s: event items plus the virtual `readMarker` and `timelineStart` items; date dividers stay on the feature side. `timeline(accountId, roomId, focus)` emits `room-unavailable` until the account holds the room, then `VectorDiff<TimelineItem>` batches that start with a `reset` and carry the back-pagination state and room state. A back-pagination emits `paginating` with no diffs, then the page's diffs and the next state in one update, so older rows and the loading flag change together; the reply follows that update. Every command replies only after its effect is in each open `timeline()` subscription, and on an account that is not live returns `account-not-live`. A send's local echo is in `timeline()` before `send` replies, and its item keeps its `uniqueId` when the remote echo replaces it; a send that fails keeps its echo, with its send state, for `retrySend` or `cancelSend`. `TimelineStore` holds one subscription per open conversation and freezes the "New messages" anchor at the first `readMarker` it sees, so reading the room does not move the divider. `TIMELINE_ENGINE` provides the `matrix-js-sdk` adapter. One contract, `defineTimelineEngineContract`, runs against `FakeTimelineEngine` in unit tests and against Synapse in `trinity-e2e-engine:contract`.

| Event item field            | Holds                                                                                           |
| --------------------------- | ----------------------------------------------------------------------------------------------- |
| `uniqueId`                  | an id that stays stable from local echo to remote echo                                          |
| `eventId`, `transactionId`  | the server id once known, and the transaction id, kept on the remote echo on the sending device |
| `sender`, `isOwn`           | the sender's user id and whether it is the account                                              |
| `timestamp`, `sendState`    | the origin time, and `sending`, `waiting` or `failed` for an own unsent echo                    |
| `content`                   | a tagged union: message, media, sticker, location, poll, state, redacted, etc.                  |
| `edited`, `inReplyTo`       | whether an edit replaced the body, and the quoted event and its details                         |
| `reactions`, `readBy`       | grouped reaction keys with capped senders, and the readers whose receipt sits here              |
| `shield`, `unencryptedMark` | a shield code (colour and reason) rather than text, and the unencrypted mark                    |
| `profiles`                  | display name and avatar for every user the item names                                           |

### Room widget engine {#room-widget-engine}

`RoomWidgetEngine` (`libs/data-access/widgets`) exposes a room's `im.vector.modular.widgets` declarations. `roomWidgets(accountId, roomId)` emits a whole `RoomWidgetSnapshot` on each change: the widgets, whether the account may manage them, and the identity a widget URL may request. An account that is not live gets an empty snapshot. `putRoomWidget` fails with `state-key-taken` when room state already holds the id, and `removeRoomWidget` fails with `conflict` once the widget's live revision is no longer the one the caller confirmed. `WidgetsService` subscribes again when the account gets a new client, and `ROOM_WIDGET_ENGINE` provides the `matrix-js-sdk` adapter. One contract, `defineRoomWidgetEngineContract`, runs against `FakeRoomWidgetEngine` in unit tests and against Synapse in `trinity-e2e-engine:contract`.

### Media engine {#media-engine}

`MediaEngine` (`libs/data-access/media`) moves media bytes. `content(accountId, request)` mints a fresh URL the webview can load on every subscription and keeps no cache; the subscriber owns it until `release` (a `blob:` URL in the `matrix-js-sdk` adapter). It fails with `media-unavailable` when there is no source or an encrypted file fails its hash check. `upload` is a command with progress: zero or more `progress` updates, then one `done` carrying the result, and unsubscribing aborts it. An encrypted upload sends neither its name nor its type, and an upload over the server's limit fails with `too-large`. `MediaService` and `AvatarService` keep their URL caches, pins and byte cap over it: `MediaService` keys an entry by account, session generation and source, so a re-login never reuses a URL from the session before, and both hand every URL they drop back through `release`. `sendAttachment` uploads a file, encrypting it when the room is encrypted, and sends one media message, as a command with progress. It fails closed with `encryption-unavailable` in an encrypted room that has no crypto. The engine keeps the upload and its local echo under the caller's `attachmentKey`, so a retry neither uploads the file again nor sends a second event, until `forgetAttachment`. `MediaPipeline` strips the file's metadata on the plaintext before handing it over, and marks a file whose strip failed so that an encrypted room refuses it. `MEDIA_ENGINE` provides the `matrix-js-sdk` adapter. One contract, `defineMediaEngineContract`, runs against `FakeMediaEngine` in unit tests and against Synapse in `trinity-e2e-engine:contract`; `assertProgressThenResult` checks the shape of a progress command.

### Expression engine {#expression-engine}

`ExpressionEngine` (`libs/data-access/media`) reads and writes the account data and room state behind custom emoji, stickers and recent emoji. `accountData` and `packRooms` are subscriptions: each emits its snapshot on subscribe and then a whole snapshot per change, never one for an unrelated type or room. `fetchAccountData` and `fetchRoomState` read the server's copy past the local store, null when absent, so a write can be verified against it. `fetchRoomState` reads a world-readable room without joining it, and `packRooms` keeps a room's name after the account leaves it. Writes are raw, so a `__proto__` key in a null-prototype map survives; an oversized write fails with `too-large` and a refused one with `kind: 'permission'`. `joinPackRoom` resolves an alias, joins unless already joined and returns the room's pack state. `EXPRESSION_ENGINE` provides the `matrix-js-sdk` adapter; `defineExpressionEngineContract` runs against `FakeExpressionEngine` and Synapse.

### Notification engine {#notification-engine}

`NotificationEngine` (`libs/data-access/notifications`) reads and writes an account's push-rule settings. `settings(accountId)` emits a whole `NotificationSettings` on subscribe and on each change: whether the rules have synced, every server-defined rule with its kind and state, the keywords, each room's mode, and the sound and reaction-notification preferences. Keywords follow matrix-rust-sdk `NotificationSettings`: each is keyed by its word and carries no sound of its own. `setKeyword` adds a rule for the word or enables one of its rules, and `removeKeyword` deletes every rule for the word. Room modes follow it too: `setRoomMode` replaces the room's own rules with the rule for the mode (`all` is a notifying room rule), and `readRoomMode` re-reads the server first. `setPreference` writes Trinity account data, whose retired names the engine reads and copies across. A command replies only once `settings` holds its effect. `notifications(accountId)` is a feed of the account's incoming notifications: live messages after the first sync that the push rules notify, never the account's own, an encrypted one once it decrypts (its rules scored on the cleartext), plus every reaction annotation by someone else. A message's text is previewed only when it arrived encrypted or the room is not encrypted. `reactionTarget` returns a reaction's target when it is the account's own message, with which of the given reactions are still live. `setPusher`, `removePusher` and `pushers` manage the account's HTTP pushers; `setPusher` always appends, because every account on the device shares one pushkey. `pushRooms(accountId)` emits the joined rooms the closed-app push renderers title notifications with (name, DM flag, and encrypted until the crypto store answers), again after each sync, rename or `m.direct` change. `PushService` registers the pushers and `PushHandoffService` mirrors each account's token and rooms to the native store, per session generation. `NotificationService` subscribes to the feed per live account and session generation, and keeps presentation, dedupe and the reaction batching. `NotificationSettingsStore` keeps one subscription per live account and session generation while the application runtime's notification session runs, so its synchronous reads hold an account's settings from the turn it goes live. `NOTIFICATION_ENGINE` provides the `matrix-js-sdk` adapter. One contract, `defineNotificationEngineContract`, runs against `FakeNotificationEngine` in unit tests and against Synapse in `trinity-e2e-engine:contract`.

### Room administration engine {#room-administration-engine}

`RoomAdministrationEngine` (`libs/data-access/room-administration`) exposes a room's administration state as plain data. `room(accountId, roomId)` emits an `AdministeredRoom`: the account's membership and power, the raw `m.room.power_levels` content, the creators and the raw content of the state events the settings read. `members(accountId, roomId)` emits every member with a display name disambiguated as js-sdk does, and asks the server for lazily loaded members. Both emit `null` while the account is not live or does not know the room, and a whole value on each change. A v12 creator's power crosses as `'infinite'`. Encryption stays `'unknown'` until the crypto store answers, so a room is never reported unencrypted before that. `setState` sends raw content, so unknown keys round-trip, and fails with `room-unavailable` in a room the account has not joined. `room-power.ts` holds the power-level rules (state and event sends, redaction, and the invite, kick, ban and redact thresholds), pinned by a spec against js-sdk's own `RoomState` answers. `AdministeredRoomStore` keeps both subscriptions per account and room behind synchronous signal reads: the first read subscribes, untracked, so permission checks inside a `computed` stay synchronous, and the subscription lasts until the account signs out or gets a new session generation. The action-permission and message and pin governance services decide from the store, and `RoomMembersService` projects its member, invite, ban and knock lists from it. `RoomSettingsService` and the power-levels editor (`RoomPermissionsService`) read the room from it and write through `setState`: the topic carries the MSC3765 `m.topic` rendering js-sdk sends, and a room photo uploads through `MediaService`. `stateEvents(accountId, roomId)` lists every current state event for the read-only state viewer (the server's `/state` in Rust), so the viewer opens once the list arrives. The server commands (kick, ban, unban, event, room and user reports, local aliases and the directory listing) fail `account-not-live` and leave every other check to the server, whose refusal arrives as `request-failed` with its status and errcode and never its text. Moderation, aliases, the directory listing and content reporting use them: a role change and the canonical alias write their content through `setState`, and reporting reads `M_NOT_FOUND` as an unknown room before a bare 404 or 405 marks the endpoint unsupported for the session. `enableEncryption` refuses a room the state or the crypto store already has encrypted (`already-encrypted`), adopts the server's `m.room.encryption` when sync missed it rather than sending a second one, and answers `encryption-not-applied` when the server has the event but this device could not apply it. Upgrading runs `upgradeRoom`, then `invite` and the `m.space.child` writes one at a time; its plan waits for the full member list and reads the linking spaces from `linkingSpaces`, so Room settings opens the upgrade dialog once the plan arrives. The timeline finds the message itself and passes its sender, so a message it does not hold is `message-unavailable` before Room Administration is asked. `ROOM_ADMINISTRATION_ENGINE` provides the `matrix-js-sdk` adapter; `defineRoomAdministrationEngineContract` runs against `FakeRoomAdministrationEngine` and Synapse.

### Contact addresses engine {#contact-addresses-engine}

`ContactAddressesEngine` (`libs/data-access/contact-addresses`) is the homeserver side of an account's contact addresses: its third-party identifiers and whether it may change them, the validation mail, adding and removing an address, the `m.identity_server` and `m.accepted_terms` account data read from the server, the OpenID token an identity server trades for its own token, and binding or unbinding an address at an identity server named in the request, never one held as client state. The identity server's own API (registration, terms, the hashed lookup and the validation mail) is plain TypeScript `fetch` in `identity-server-http.ts`; its lookup sends only sha256 hashes with the server's pepper and refuses a server that offers no sha256. `IdentityServerService` combines the two. Adding an address answers the homeserver's re-authentication as data: `addThreePid` fails `uia-required` with the challenge, and `EmailAddressesWorkflow` runs it through the shared `driveUia` loop. `CONTACT_ADDRESSES_ENGINE` provides the `matrix-js-sdk` adapter; `defineContactAddressesEngineContract` runs against `FakeContactAddressesEngine` and Synapse, whose mail cases need the harness's Mailpit and identity cases Sydent too.

### Auth engine {#auth-engine}

`AuthEngine` (`libs/data-access/auth`) carries sign-in and password commands as plain data. Most take a homeserver URL rather than an account: the login flows, the OAuth 2.0 auth metadata (`null` from a server that answers without it), username availability, the SSO redirect URL, password and login-token sign-in, and the email password reset. A sign-in returns the session's user, device and tokens, which `AuthService` establishes as an account. The server refusing a sign-in fails `login-refused` with `invalid-credentials` (password), `invalid-token` (an expired or spent login token) or `deactivated`. `changePassword(accountId, …)` keeps the account's other sessions signed in. A request the server answers with user-interactive auth fails `uia-required` with the challenge; `driveUia` answers it through `engineUia`, which sends the request again with its `auth`. A weak password's reason crosses as the `serverMessage` param. `AUTH_ENGINE` provides the `matrix-js-sdk` adapter. One contract, `defineAuthEngineContract`, runs against `FakeAuthEngine` in unit tests and against Synapse in `trinity-e2e-engine:contract`, where the reset cases confirm the link Synapse mails to Mailpit; without Mailpit they skip, and the runner fails on skips.

## Treat synchronization as authoritative {#sync-authority}

Commands call the SDK and then allow sync or the relevant SDK event to reconcile current state. Preserve a typed error or outcome for the initiating action, but do not claim that an accepted network request has already become authoritative local state unless the SDK contract guarantees it.

Authentication, persistence, and cryptographic storage require stronger lifecycle rules than ordinary Matrix reads. When a homeserver offers both OAuth 2.0 sign-in and legacy SSO, Trinity prefers OAuth 2.0, because only that flow lets the client check that the sign-in response comes from the provider it started with.
