# Documentation ownership and migration map

This is the working inventory for [Create task-based documentation entry points](https://github.com/quwisky/trinity-matrix-client/issues/533)
and the [documentation rewrite map](https://github.com/quwisky/trinity-matrix-client/issues/543).
It records destinations and ownership, not a claim that the linked content has already been rewritten.
The baseline is `refactor/refine-architecture` at `dbd200ce3b6c289d9dea291d52947658dedc621c`,
which includes the merged agent-workflow changes from PR #532.

## Reader paths

Architecture, platforms and shared references remain supporting topics rather than competing
reader entry points. Keep useful existing paths: task-based navigation does not require moving
all technical references. Destinations shown as code below are migration targets; link readers
to the current working guide until its replacement exists.

## Ownership and migration rules

- Each row names the content owner for its rewrite. The navigation slice creates the entry
  points and this inventory; later slices own their substantive topics. Integration owns the
  shared landing pages, final link reconciliation and this inventory's completion status.
- Each slice edits its owned guide and local task navigation. For a shared file (root README,
  documentation landing page, command/troubleshooting reference, contribution conventions),
  send the exact proposed section change to the coordinator. Keep one writer per file; the
  coordinator applies shared edits after incorporating the owning slice. Release policy sections
  are supplied by Maintenance, UI sections by UI, and host details by Hosts.
- Move a guide only when the substantive replacement is ready. Update its inbound links in
  the same change and retain a short old-path pointer during parallel work. Final integration
  searches all first-party references before removing obsolete pointers or plans.
- Verify links, anchors, formatting and the changed reader journey in every slice. Accuracy
  evidence records the inspected revision and actual commands/checks, including unavailable
  native or service-dependent checks. Existing linked guides are useful but not yet audited.
- Preserve ADRs and historical release/validation evidence. An obsolete plan is removable only
  after extracting active requirements and identifying the living contracts that replace it.
  The final integration slice verifies those dispositions rather than bulk-deleting migration docs.

  adding a navigation link does not certify a feature or an open proposal as delivered.

  check those references against this effort's integration baseline when rewriting their guides.

  validation report is historical evidence. Keep that distinction when reorganizing them.

  extract the remaining requirements before Integration removes the superseded plan.

  actual configuration and rules rather than promising an untested automatic workflow.
- Commands, host procedures, CI and release instructions still need their owning slices' accuracy
  checks. No application runtime, release or native-device validation is claimed by this inventory.
