# Conventions

Some of what follows is enforced by ESLint, Stylelint, Prettier or a git hook, and
some of it is convention held up by nothing but this page. Both kinds are listed,
and each one says which it is, because knowing that changes how carefully you have
to hold it.

## Component files

Each component lives in its own directory, named after itself, with four files:

```text
libs/feature/auth/src/lib/login/
├── login.page.ts
├── login.page.html
├── login.page.scss
└── login.page.spec.ts
```

Logic in the `.ts`, template in the `.html`, styles in the `.scss`. No inline
templates or inline styles for anything that is not trivial. Pages are named
`*.page.*` and everything else `*.component.*`.

The repository keeps soft size targets rather than hard limits: roughly 150 to 250
lines for a component `.ts`, 100 to 200 for a template, with a refactor threshold
around 300 to 400. A cohesive long file is fine; a tangled short one is not. The
usual split is extracting child components out of a large template, or moving
workflow logic into a service.

## Selectors and class names

| Rule                              | Value                                   | Enforced by                              |
| --------------------------------- | --------------------------------------- | ---------------------------------------- |
| Element selectors                 | `trn` prefix, kebab-case — `trn-avatar` | `@angular-eslint/component-selector`     |
| Attribute selectors on directives | `trn` prefix, camelCase                 | `@angular-eslint/directive-selector`     |
| Component class names             | Must end in `Page` or `Component`       | `@angular-eslint/component-class-suffix` |

`libs/spartan/**` is exempt from those three plus `no-input-rename`. That code is
generated by `@spartan-ng/cli` and uses `hlm` and `brn` prefixes, unsuffixed class
names like `HlmButton`, and aliased inputs including `class`. Exempting it beats
fighting the generator on every re-sync. The exemption is itself pinned by a spec —
see [CI and releases](ci-and-releases.md#the-lint-invariants-spec) — which fails if it
ever widens beyond those four rules.

## Change detection and templates

Every first-party component declares
`changeDetection: ChangeDetectionStrategy.OnPush` — all 76 of them, with no
exceptions in the tree today. Nothing enforces it, so it is on you to keep that
true.

Use Angular's built-in control flow — `@if`, `@for`, `@switch`. There is not a single
`*ngIf` or `*ngFor` anywhere in `libs/` or `apps/`, and `CommonModule` is imported
nowhere, so there is no legacy pattern to copy from.

Two bans with direct replacements:

| Do not use | Use instead             |
| ---------- | ----------------------- |
| `ngClass`  | `[class.is-active]="…"` |
| `ngStyle`  | `[style.width.px]="…"`  |

And do not use the `@HostBinding` or `@HostListener` decorators. Put host bindings in
the `host` object of the decorator metadata, which is also where static attributes
and test hooks belong:

```ts
@Component({
  selector: 'trn-media-bubble',
  changeDetection: ChangeDetectionStrategy.OnPush,
  host: {
    'data-testid': 'media-bubble',
    '[attr.data-media-kind]': 'kind()',
    '[attr.data-media-state]': 'state()',
  },
  templateUrl: './media-bubble.component.html',
})
```

There are zero occurrences of `@HostBinding`, `@HostListener`, `ngClass` and
`ngStyle` in first-party code. Again: convention, not a lint rule.

## Forms are Signal Forms, and only Signal Forms

The workspace is 100% `@angular/forms/signals`. There is no `FormControl`, no
`FormGroup`, no `ReactiveFormsModule`, and no `ngModel` anywhere in `libs/` or
`apps/`. Ten components use Signal Forms today, and there is deliberately no legacy
idiom left to imitate.

The form is a signal over a model object, which is the same reactive model as the
rest of the app. Build it with `form(model, schema)`, bind native controls with
`[formField]`, and put the `<form>` element under `[formRoot]`.

```ts
readonly form = form(this.model, (path) => {
  required(path.name);
  disabled(path.joinRule, { when: () => !this.canEditJoinRule() });
});
```

```html
<form [formRoot]="form" (submit)="save()">
  <input hlmInput [formField]="form.name" />
</form>
```

Two traps are worth stating outright.

!!! warning "A field's disabled state belongs to the schema"

    Binding `[disabled]` on a node that also has `[formField]` is a compile error,
    NG8022. Unit tests will not catch it, because Vitest transpiles without type
    checking; `pnpm build` will, because the production build runs the Angular
    compiler. Express it as `disabled(path, { when: … })` instead — and it must be
    the `{ when }` **object** form, since passing a function or a string directly is
    deprecated and the type-aware `@typescript-eslint/no-deprecated` rule fails the
    build on it.

`[formRoot]` is not decorative either. It sets `novalidate` and calls
`preventDefault()` on submit for you. A bare `<form>` whose only binding is a control
triggers a native submit and a full page reload.

## Imports and boundaries

Cross-library imports go through `@trinity/*` path aliases declared in
`tsconfig.base.json`. Imports **within** a library stay relative. That is not style
advice: `@nx/enforce-module-boundaries` errors on a same-project alias import with
"Projects should use relative imports to import from other files within the same
project", and because the rule is an error it fails the pre-commit hook, not just CI.

Which library may import which is decided by `type:*` and `scope:*` tags in each
project's `project.json`. The ladder and the reasoning behind it are in
[Libraries](../architecture/libraries.md); the rule contributors hit most often is
that a `type:feature` library may never import another `type:feature` library.

Two barrels are deliberately incomplete, and nothing enforces either:

- `libs/feature/shell/src/index.ts` does not re-export `home.page`. That barrel is
  eagerly imported by `main.ts` for `AppComponent`, so anything in it ships in the
  eager chunk. The page is reached through the `@trinity/feature/shell/home-page`
  alias instead.
- `code-highlight.ts` is kept out of the `util-matrix` barrel and reached through
  `@trinity/util-matrix/code-highlight`, because `message-view.ts` is eager and the
  Shiki grammars are roughly 813 kB raw.

Adding either to its barrel ships a large payload into the initial bundle with no
error anywhere.

## Styles

Component styles live in the component's own `.scss`. Reference the `--trinity-*`
design tokens rather than hardcoding colours, or the component will not re-theme with
light or dark mode or with a palette change — the details, including which token is a
text colour and which is a fill, are in
[UI and theming](../architecture/ui-and-theming.md).

Shared SCSS mixins live in
[`libs/feature/rooms/src/lib/styles/_mixins.scss`](https://github.com/quwisky/trinity-matrix-client/blob/develop/libs/feature/rooms/src/lib/styles/_mixins.scss):
`ellipsis`, `category-label`, `profile-card`, `dialog-surface($width)`,
`column($background)`, `interactive-row` and `scrollable`.

Stylelint runs `stylelint-config-standard-scss` over `{apps,libs}/**/*.scss`, and it
is a **separate** command from `pnpm lint` and a separate CI step. Running `pnpm lint`
alone will not catch a SCSS violation.

## Keep the data-testid hooks

Interactive elements carry `data-testid` attributes, and the headless Playwright
harnesses drive them — around 290 distinct hooks across the templates. Renaming or
dropping one breaks an end-to-end spec in a way that reads as a product regression
rather than a renamed selector. When you move an element, move its hook with it.

## Commits

Commits follow [Conventional Commits](https://www.conventionalcommits.org/):
`type(scope): subject`. The `commit-msg` hook runs commitlint against
`@commitlint/config-conventional`, so a malformed message is rejected locally.

| Type       | For                                           |
| ---------- | --------------------------------------------- |
| `feat`     | A new feature                                 |
| `fix`      | A bug fix                                     |
| `docs`     | Documentation only                            |
| `style`    | Formatting or whitespace, no behaviour change |
| `refactor` | Restructuring without behaviour change        |
| `perf`     | Performance work                              |
| `test`     | Adding or updating tests                      |
| `build`    | Build system, tooling, or dependency changes  |
| `ci`       | CI configuration changes                      |
| `chore`    | Maintenance touching neither source nor tests |
| `revert`   | Reverting a previous commit                   |

The subject is lowercase and imperative — "add keyword rules", not "added keyword
rules". A breaking change takes a `!` after the type or scope, or a
`BREAKING CHANGE:` footer. Never use a bare "fix", "update" or "WIP" as the whole
message.

Branches are named `type/short-description`: `feat/user-auth`, `fix/login-crash`,
`chore/update-deps`. Cut them from `develop`, which is the repository's default base
and what `nx affected` diffs against.

Every feature, bug fix or breaking change gets an entry under `## [Unreleased]` in
`CHANGELOG.md` before it is done. Entries are written for humans: describe the impact,
not the implementation. Version numbers are **not** touched in ordinary work commits —
they move only in a dedicated release commit alongside the changelog rename, and both
`package.json` and `electron/package.json` must agree with the tag or the release
workflow refuses to build.

## Hooks and formatting

`prepare: "husky"` installs the hooks on `pnpm install`. There are two.

| Hook         | Runs                               |
| ------------ | ---------------------------------- |
| `pre-commit` | `pnpm exec lint-staged`            |
| `commit-msg` | `pnpm exec commitlint --edit "$1"` |

`.lintstagedrc.json` has exactly four entries:

| Staged files                                       | Applied                                              |
| -------------------------------------------------- | ---------------------------------------------------- |
| `{apps,libs,electron}/**/*.ts`                     | `eslint --fix --no-warn-ignored`, `prettier --write` |
| `*.scss`                                           | `stylelint --fix`, `prettier --write`                |
| `*.{js,cjs,mjs,mts,cts,json,css,md,yaml,yml,html}` | `prettier --write`                                   |
| `capacitor.config.ts`                              | `prettier --write`                                   |

Note what the TypeScript glob does not reach: `scripts/`, `e2e/` (globally ignored by
ESLint anyway), and any root-level `.ts` file. Those get Prettier and nothing else.

Prettier owns formatting across the repository, verified in CI by
`pnpm format:check`, which exits non-zero on drift. Every file therefore ends with a
trailing newline — Prettier writes one, so a file without it fails the check.
`.prettierignore` carves out the native projects, generated output, and the generated
`libs/spartan/**/hlm-*.ts` files, which are left in the generator's own class order so
a re-sync does not fight `prettier-plugin-tailwindcss`.

## Deprecated APIs are an error

`@typescript-eslint/no-deprecated` is the workspace's one type-aware rule, scoped to
`{apps,libs,electron}/**/*.ts` and excluding specs and config files. Using an API
marked `@deprecated` — in Angular, in matrix-js-sdk, or in this repository's own
code — fails the lint run. Replace it with the recommended alternative rather than
suppressing it.

This has a consequence when you deprecate something yourself. The rule is type-aware,
so a project's lint result depends on its **dependencies'** source, which is where the
`@deprecated` tag lives. `nx.json` gives the `lint` target `^production` inputs for
exactly that reason; without them, deprecating an export in `util-matrix` would leave
every consumer reporting a cached pass, and the ban would silently stop working across
the boundaries it exists to police.
